Thimble · a 44M-parameter function caller

A small model that turns a sentence into a function call

A smart speaker, a watch, a robot vacuum — each exposes its abilities as typed functions, and each needs something to translate “dim the kitchen to thirty” into set_lights(room="kitchen", brightness=30). Today that translation usually costs a network round trip to a model with billions of parameters, most of which exist to write prose nobody asked for.

Thimble does only the translation. It reads a catalog of tools and a user request and returns the calls to make, or an empty list when nothing in the catalog fits. It cannot hold a conversation and never sees prose in training. At 44 million parameters it is small enough to run on a phone, and narrow enough to beat models sixty-eight times its size at this one job.

What follows is how it works, what it scores, and — at some length — the ways the comparison flatters it.

The contract

Input, output, and nothing else

The interface is deliberately narrow. Declare your tools as JSON Schema, hand over a user message, get back a canonical array of calls. Arguments are typed and sorted; optional arguments appear only when something in the query licenses them; the array is schema-valid by construction rather than by inspection.

When a request falls outside the catalog — “tell me a joke”, “what's the capital of France” — the model returns an empty array instead of inventing a plausible-looking call. Refusal is a trained decision with its own place in the grammar, not an accident of sampling.

The bet

Tool calling is five decisions, not a generation problem

Most tool-calling models are language models that write JSON. Thimble is a language model that makes five decisions, with the JSON assembled around it by a compiler.

Consider what a tool call actually requires. Given a query and a catalog of typed functions, something must decide whether any tool applies, which one, which optional arguments the query licenses, what values fill them, and whether another call follows. That is the entire problem. Every other token in the output — the braces, the quotes, the commas, and critically every argument key — was fixed by the schema before the model ran.

A model that generates JSON as text spends real capacity learning that { follows [, and spends it again on every call it makes. At 44 million parameters that capacity does not exist, so we decline to spend it: a grammar compiled from the declared schemas emits the structure, and the model is consulted only where a genuine choice exists.

The consequence is worth stating precisely, because it is stronger than the usual claim made for constrained decoding. Malformed JSON, hallucinated argument names, and calls to tools that were never declared are not rare in Thimble's output. They are unreachable: no sequence of model decisions produces them.

The diagnosis

Where Needle actually loses

Needle 2's own table is the most interesting thing in their release: 98.3% name accuracy, 63.7% overall, 48.4% on two-call rows. They almost never pick the wrong tool. They lose on argument values, and on second calls that never get made.

The second number is a mechanism, not a mystery.

Their pipeline retrieves the top five tools once, then generates the call array as tokens. If the second call needs a tool outside that initial set, it was never a legal option — the model cannot recover, however well it understood the request. The fix appears in a paper they don't cite: DTDR conditions retrieval on the query plus the calls already emitted. We re-run retrieval between array elements and swap the grammar's legal name set mid-generation.

The model

A trunk, three heads, and a compiler

A deep-thin transformer — d=448, 20 layers, GQA 8/4, SwiGLU, an 8k BPE vocabulary with tied embeddings, QK-norm, sandwich normalization, gated attention — carrying three capabilities.

A retriever

Ranks the catalog against the query and the partial plan, re-running between array elements. This is the DTDR fix above, and it is where the two-call number comes from.

A name head

A bilinear readout scoring the decision-position hidden state against each candidate's name span in the prompt. The motivation is “Looking Is Not Picking”: models attend to the correct tool 80% of the time and still choose wrong. Tool selection fails at the readout, not at perception — readout-side interventions recover 59–91% of failures, prompt-side fixes at most 23%. So we replaced the readout with a trained one.

A grammar-constrained argument decoder

The tokenizer holds a hard contract: JSON structural characters are singleton tokens that never merge into anything else. No token can straddle a structure/value boundary, so the compiler force-feeds structure exactly and consults the model only at the five points in Fig 2.

We deliberately did not clone Needle's Simple Attention Network. Their own paper prices that architecture against a matched-parameter transformer at 0.006 nats. The mixer was never the bottleneck. How the forward pass is spent is.

The other comparison

One person, one day, one rented GPU

Needle 2 lists eight authors. It was pretrained on a proprietary 115-billion-token corpus across TPU pods, then post-trained on another 38 billion, with a custom C++ inference engine and a quantization scheme built alongside it. It is a serious piece of engineering by people who do this professionally.

This was one person without a machine-learning background, working with an AI agent for a single day, on a $0.22-an-hour rented gaming GPU. No pretraining run. No custom kernels. About 122 million training tokens — roughly 1,250× fewer than Needle saw.

The point is not that the professionals were wrong. Every architectural idea here came from reading their work and the literature around it. The point is what the gap between those two columns now costs to cross.

Fair warning

What is unfair about this comparison

Cactus states their asymmetries openly. So will we — in both directions.

Precision favors us

We report bf16. Needle reports CQ2-bit, measured end to end through a shipped C++ binary with a 256-token sliding window and cache eviction live. Quantizing to two bits will cost accuracy we have not yet paid.

Domain adaptation favors us

Mobile Actions' train split — 8,693 public rows, disjoint from eval — is in our mix. Needle trained on its own device-action corpus. Our eval rows were never seen, so the number is clean; but this is a domain-adapted model measured against a generalist.

Deployment favors Needle, enormously

They ship a dependency-free 14MB binary that runs on an ESP32 inside a 28MB RAM ceiling, with 2-bit quantization trained in from pretraining onward. We have a 168MB bf16 checkpoint and no engine. On the axis they actually optimized for, we are not competitive.

The bill

One working day, twenty-six dollars

The expensive thing was never the compute. It was knowing which 146,000 rows to build, and that came from reading failures rather than from scale.

Post-mortem

The first checkpoint scored zero

Not low. Zero. It refused half the rows outright and mis-selected the rest.

The cause was not capability. It was shape: we trained on catalogs of three to nine tools, and Mobile Actions presents ten to sixteen, with a date-and-time preamble on every query that our data never contained. The model had never seen the form of the question. Adding catalog augmentation and preambles moved it from 0.0 to 80.1.

Four bugs surfaced by probing intermediate checkpoints, each of which would have silently corrupted the headline:

  1. Value truncation at 24 tokens. Email bodies cut mid-sentence, failing exact match on rows the model had otherwise answered perfectly.
  2. A device mismatch in the head/LM ensemble that crashed every constrained decode the moment it ran on GPU.
  3. Tokenizer alignment breaking on non-ASCII. <unk> is a five-character token string standing in for one character, silently desynchronizing every loss tag after it.
  4. A schema that lies. Mobile Actions advertises datetimes as YYYY-MM-DDTHH:MM:SS; its gold values use a space separator. We had written a grammar template from the schema text. Checking gold data instead of trusting prose caught it before it cost 365 rows.

Still open

What we don't know yet

The name head is on probation. Against the same-trunk control it wins by 1.5 points out of distribution with a small training set, and ties once the training set is large. The plan says we drop the heads if they cannot beat the control. That verdict is pending on the harder suites.

Seal-Tools, DroidCall, BFCL v4 and ACEBench are still running or unbuilt, and no claims are made about them here. Seal-Tools matters most: it holds out entire domains, which is the real test of whether the architecture generalizes or whether we simply learned Mobile Actions.

And two-bit. Everything above is bf16. Needle's genuine achievement is that their 14MB artifact is the model they trained. Ours is not quantized at all, and that is the honest distance between a benchmark result and something you can put inside a doorbell.
